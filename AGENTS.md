# Правила разработки сайта «Надеждик»

Адаптировано из `../alex_evgenygrigoriev/template_AGENTS.md`. Правила относятся к работе
над сайтом «Надеждик» в этом проекте.

## Контекст проекта

- Продуктовый бриф: [PRODUCT.md](PRODUCT.md). Сайт охватывает все направления «Надеждика».
  Основное действие — заявка, после которой с родителем связывается администратор.
- Исходные публичные источники: https://nadezhdik.ru/ и https://vk.ru/nadezhdik.project.
  Подтверждённые сведения, даты проверки и пробелы перечислены в PRODUCT.md.
- Реализована локальная главная: `index.html`, `src/styles.css`, `src/main.js`;
  статические материалы — `public/`, результат сборки — `dist/`. Бриф, DESIGN.md,
  оригиналы маскота и исследование сохраняются отдельно.
- Стек: семантический HTML, CSS, JavaScript без сторонних runtime-зависимостей, Node.js 22+.
  `npm run dev` — локальный сервер исходников, `npm run check` — синтаксические проверки,
  `npm run build` — пересоздание `dist/`, `npm run preview` — просмотр сборки.
  Сервер по умолчанию: http://localhost:4173, порт меняется через `PORT`.
  Относительные URL поддерживают размещение в подкаталоге; серверная маршрутизация не нужна.
  Хостинг и публикация не настроены. Обращения ведут в сообщения ВКонтакте;
  серверной формы, CRM и согласованных правовых текстов пока нет.
  Фактические проверки и ограничения: [отчёт](docs/research/homepage-2026-11-02/README.md).
- PRODUCT.md хранит сведения о продукте, аудитории, сценариях и объёме работ.
  DESIGN.md хранит выбранное визуальное направление и решения по дизайну.
  В docs/research/ сохраняй результаты исследования, реестр материалов и подтверждения;
  наличие референсов не означает готовности всех материалов к публикации.
- В рамках правки документации проверяй документы и согласованность требований.
  Браузерные проверки и сборка ниже относятся к реализованному сайту; их нельзя отмечать
  выполненными до появления кода и фактической проверки.

## Цель и приоритеты

Создавай сайт под конкретный продукт, аудиторию и бренд. Качество оценивай по содержанию,
самостоятельности визуального решения, удобству, доступности и производительности.
Не обещай «неопределимость ИИ-происхождения»: эти правила не являются детектором генерации.

Явные требования пользователя, достоверные сведения о продукте и правила этого файла имеют приоритет над стилистическими предпочтениями скиллов. Сохраняй понятные паттерны навигации и взаимодействия. Не добивайся оригинальности ценой удобства.

## Обязательные требования качества

### 1. Определи содержание и направление до реализации

- Прочитай бриф, существующий сайт, PRODUCT.md и DESIGN.md, если они есть. При локальной
  доработке сохраняй сложившуюся идентичность вне запрошенных изменений.
- Зафиксируй аудиторию, задачу посетителя, уместное основное действие, особенности продукта,
  подтверждённые факты, доступные материалы и пробелы. Используй PRODUCT.md или существующий бриф.
- Если нет содержательного брифа, подготовь техническую основу и список недостающих сведений.
  Не изобретай бизнес, услуги, цены, контакты, достижения или призывы к действию.
- Если направление не задано, кратко сравни 2–3 концепции, различающиеся идеей, композицией
  и ролью изображений. Замены цвета и шрифта недостаточно. Выбери подходящую с кратким обоснованием.
- Запиши в DESIGN.md визуальную идею, её связь с продуктом, принципы композиции, типографики,
  цвета, изображений и движения. Для небольшой правки используй существующую запись.
- Обычные решения принимай самостоятельно. Уточняй только то, что существенно меняет задачу
  и не следует из доступных материалов. Требования к утверждению концепции бери из поручения.

### 2. Построй структуру из вопросов посетителя

- Для каждой секции определи вопрос посетителя, ответ и материал, который его подтверждает.
  Удали секции, не помогающие понять предложение или выполнить задачу.
- Выбирай формат по содержанию: текст, список, фотография, таблица, схема, демонстрация, кейс.
  Не собирай все сайты по схеме «первый экран → преимущества → процесс → цифры → отзывы → FAQ».
- Сохраняй смысл и полноту информации. Не выравнивай длину текстов ценой содержания
  и не помещай всё в карточки ради одинаковой геометрии.
- Первый экран должен объяснять, что это за предложение и кому оно нужно. Действие,
  если оно уместно, называй по результату: посетитель понимает, что произойдёт после нажатия.

### 3. Используй достоверные материалы

- Не выдумывай клиентов, отзывы, награды, сертификаты, партнёров, показатели и интерфейсы продукта.
  Не заменяй объяснение предложения словами «инновационные решения» или «новый уровень».
- Недостающие факты перечисляй в рабочих заметках. Макеты и демонстрационные данные явно
  обозначай в прототипе; не выдавай их за реальные сведения на опубликованном сайте.
- Используй материалы проекта или подходящие изображения с проверенным происхождением
  и правами использования. Генерация допустима для иллюстраций и концептов, но не как
  свидетельство существования команды, продукта, помещения или результата работы.
- Сохраняй исходники отдельно от производных. Записывай источники, лицензии и промпты
  в docs/research/ или принятом в проекте месте. Проверяй производные рядом с оригиналом.

### 4. Свяжи визуальный язык с предметом

- Выводи визуальную идею из особенностей продукта, его материалов, места, процесса или результата.
  «Современно», «премиально» и «технологично» сами по себе не задают направление.
- Выбирай шрифты по характеру бренда, читаемости, языкам и доступным начертаниям.
  Проверяй реальную загрузку, кириллицу при её использовании, переносы и резервный шрифт.
  Не назначай один обязательный шрифт или универсальную пару всем проектам.
- Создай согласованные роли цвета, размеров, отступов и компонентов. Иерархия должна быть
  заметна по композиции и масштабу. Варьируй структуру секций, когда этого требует содержание;
  повторение полезно для сопоставимых сущностей и привычных элементов интерфейса.
- Референсы изучай в браузере. Записывай переносимые принципы и наблюдения со скриншотами,
  а не копируй чужие тексты, логотипы, изображения или узнаваемую композицию целиком.
- Для сайта со сценами используй мотив, связанный с продуктом: раздельные планы, смену среды,
  масштаб и устойчивую область текста. Каждый переход должен раскрывать содержание.
  Не добавляй персонажа, 3D, параллакс или закрепление экрана только ради эффекта.
- Не устанавливай квоты на картинки, анимации, размеры заголовков или число разных композиций.
  Статичная страница допустима. Удаление украшений должно усиливать содержание и иерархию.

### 5. Обеспечь работающий и доступный интерфейс

- Ссылки ведут к заявленной цели; кнопки выполняют действие. Формы, поиск и фильтры работают
  в согласованном объёме. Не показывай успех отправки без фактической отправки данных.
- Проверь применимые состояния: ожидание, загрузку, ошибку, успех, отсутствие данных,
  недоступность действия. Сообщения объясняют результат и способ продолжить работу.
- Используй семантическую разметку, доступные имена, подписи полей, видимый фокус,
  клавиатурное управление и достаточный контраст. Не передавай смысл только цветом или hover.
- Движение объясняет связь, продукт или результат действия. Не применяй одинаковый fade-up
  ко всем блокам и подъём при наведении ко всем карточкам.
- Учитывай prefers-reduced-motion. Содержимое лендинга доступно без JavaScript;
  при отказе анимации текст и ссылки остаются видимыми. Интерактивным функциям обеспечь
  понятное сообщение или запасной путь, если они требуют JavaScript.
- Сохраняй обычную прокрутку. Сценам с pin/scrub обеспечь читаемую мобильную и статичную версии.
  Оптимизируй изображения, шрифты и движение; выбирай сложность по пользе и измеренной плавности.

## Решения, которых избегать по умолчанию

Следующие приёмы допустимы, если решают конкретную задачу или следуют явному брифу.
Их наличие не доказывает генерацию. Проверяй назначение, частоту и сочетание:

- Стрелки ↗ и → у каждой ссылки, кнопки и карточки; искры, звёзды, молнии, ракеты и щиты
  как универсальный декор; маленькие иконки в цветных скруглённых квадратах.
- Плашка над каждым заголовком; обязательное градиентное, курсивное или подчёркнутое слово;
  английские подписи, разреженный капс, моноширинные микроподписи и номера секций ради антуража.
- Фиолетовые градиенты, светящиеся пятна, фоновые сетки, шум, стеклянные панели и тени
  на всех поверхностях; одинаковые скругления и кнопки-капсулы повсюду.
- Bento-сетки и три равные карточки независимо от содержания; бегущие строки,
  бесконечные карусели, декоративные графики и условные панели с произвольными числами.
- Бежевый фон с крупными засечками, золотой «люкс» или чёрный фон с кислотным акцентом
  как универсальный ответ на любой бриф. Не заменяй один повторяющийся стиль другим.

Сам по себе inline SVG, viewBox="0 0 24 24" или aria-hidden="true" не является проблемой.
Проверяй видимый элемент и его функцию; сохраняй корректную разметку доступности.
Стандартные иконки поиска, закрытия и раскрытия допустимы там, где помогают взаимодействию.

### Порядок применения

- Основная последовательность: Taste помогает выбрать направление; Impeccable прорабатывает
  и проверяет интерфейс; Emil подключается точечно для компонентов и движения.
  Читай соответствующий SKILL.md и только нужные references, не весь набор сразу.
- При существующем DESIGN.md сохраняй выбранное направление. Не запускай второй независимый
  процесс выбора концепции через Impeccable или общий frontend-design.
- Для Impeccable выбирай нужную команду внутри одного скилла: `layout`, `typeset`, `clarify`
  при реализации; `critique`, `audit`, `adapt`, `harden`, `polish` при проверке.
  Отдельные скиллы с этими именами не установлены. Команда Impeccable `animate` и скилл
  Emil `animate` — разные точки входа; выбирай одну по задаче.
- PRODUCT.md уже содержит продуктовый контекст. Не запускай `init` ради установки
  и не перезаписывай бриф автоматически. DESIGN.md создавай в рамках задачи проектирования.
- `review-animations`, `pick-ui-library` и `prototype` имеют
  `disable-model-invocation: true`: вызывай их только явно, согласно их метаданным.
  Наличие остальных скиллов также не означает, что их нужно применять к каждой правке.
- Нативные скиллы, Sonner и подбор библиотек не задают стек сайта. Не добавляй зависимости
  только ради того, что соответствующий скилл установлен.
- Скиллы доступны как файлы проекта; автоматическое обнаружение ожидается со следующего хода.
  Если каталог скиллов не обновился, открой нужный локальный SKILL.md напрямую.
  Инструменты, браузеры и библиотеки проверяй отдельно в текущей сессии.
- Примеры явных вызовов в Codex: `$design-taste-frontend`, `$impeccable audit`,
  `$emil-design-eng`. Аргументы и ограничения сверяй с локальным SKILL.md.

### Запуск и обслуживание

- Taste использует Node.js 22+; команды запускаются из корня проекта. Проверка установки:
  `node .agents/skills/design-taste-frontend/scripts/draw.mjs --list sectors`.
  Браузерный инспектор дополнительно требует установленный Chrome, Edge или Chromium.
- Impeccable поставляется с launcher и закреплённой версией движка. Для локального кеша
  запускай его с `IMPECCABLE_HOME="$PWD/.impeccable/cache"`. Проверка движка:
  `IMPECCABLE_HOME="$PWD/.impeccable/cache" .agents/skills/impeccable/scripts/impeccable engine-probe`.
  Первый запуск при отсутствии движка скачивает бинарный файл и проверяет его по комплектному
  SHA-256 манифесту. Рабочий `context` запускай по инструкции скилла только при его применении.
- Автоматические hooks, расширения браузера и регистрация дополнительных агентов этой
  установкой не настраиваются. Наличие файлов agents внутри upstream-набора не означает
  регистрацию в конфигурации Codex. Проверки запускаются явно.
- Проверка целостности установленных файлов из корня проекта:
  `sha256sum --check .agents/skill-sources/SHA256SUMS`.
  При обновлении сначала сравни upstream-изменения; обнови выбранные наборы, ревизии,
  лицензии и контрольные суммы вместе. Не меняй оригиналы скиллов ради правил проекта:
  локальные уточнения записывай здесь.

### Общие требования к средствам

- В этом проекте стилистические запреты скиллов считаются рекомендациями для ревью.
  Квоты на изображения и движение, обязательный интерактивный аттракцион, универсальные
  ограничения строк, шрифтов, цветов и радиусов не применяются. Требования достоверности,
  доступности и работоспособности обязательны. Не добавляй декор ради прохождения детектора.
- Автоматические проверки отделяй от эстетических оценок. Ошибки сборки и доступности исправляй;
  спорное стилевое предупреждение сопоставляй с брифом и кратко объясняй принятое решение.
  Не объявляй проверку успешной, если инструмент вернул ошибку; укажи её применимость.
- Для простой обратной связи достаточно CSS. GSAP и другие библиотеки движения выбирай
  только для конкретной задачи; API и приёмы оптимизации проверяй по официальной документации.
  Не устанавливай библиотеки ради стиля.
- Imagegen используй при потребности в растровых материалах; перед редактированием осмотри исходник.
  Для работы из Figma подключай соответствующий скилл только при наличии такой задачи.
- Для браузерных проверок в текущей сессии доступен Playwright MCP; в следующих сессиях
  проверь его доступность или используй существующее средство проекта.
  Актуальные API уточняй по официальной документации.
  Не объявляй инструмент установленным, вызванным или проверенным без соответствующего факта.
- Дополнительные скиллы выбирай для установленного пробела: например, сложной доступности,
  исследования пользователей или измерения производительности. Не добавляй ещё один общий
